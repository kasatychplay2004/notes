# Лаба 3: анализ ARP-таблицы

**Модуль 1, сессия 4** · Инструмент: `arp -a`

## Цель

Проверить ARP-таблицу рабочей станции на признаки спуфинга,
разобрать состав записей.

## Вывод команды
Интерфейс: 192.168.1.71 --- 0xb
адрес в Интернете Физический адрес Тип
192.168.1.1 e0-0e-e4-cd-e1-06 динамический
192.168.1.255 ff-ff-ff-ff-ff-ff статический
224.0.0.2 01-00-5e-00-00-02 статический
224.0.0.22 01-00-5e-00-00-16 статический
224.0.0.251 01-00-5e-00-00-fb статический
224.0.0.252 01-00-5e-00-00-fc статический
239.255.255.250 01-00-5e-7f-ff-fa статический
255.255.255.255 ff-ff-ff-ff-ff-ff статический
---

## Проверка на спуфинг

**Дубликатов MAC нет** — каждый физический адрес встречается один раз
(кроме служебных broadcast/multicast, где это нормально).
Признаков ARP spoofing не обнаружено. ✅

Быстрая проверка на практике сводится к одному действию: пробежаться
по колонке физических адресов и убедиться, что один MAC не числится
за несколькими IP.

---

## Разбор записей

### Шлюз
192.168.1.1 e0-0e-e4-cd-e1-06 динамический
**Совпадает с данными из лабы 1**, где этот же MAC (вендор DWnetTechnol)
фигурировал как адрес назначения в исходящих пакетах.

Подтверждение теории: для всего внешнего трафика используется
один-единственный MAC — адрес шлюза. IP-адреса удалённых серверов
в ARP-таблице не появляются никогда.

Тип **динамический** — запись получена по ARP и живёт несколько минут.

**Наблюдение:** IP станции сменился с .72 (лаба 1) на .71 — адрес выдан
DHCP на ограниченный срок и может меняться при переподключении.

### Broadcast
192.168.1.255 ff-ff-ff-ff-ff-ff
255.255.255.255 ff-ff-ff-ff-ff-ff
`192.168.1.255` — broadcast-адрес подсети `192.168.1.0/24`
(последний адрес диапазона).
`255.255.255.255` — широковещание в пределах сегмента, используется
когда устройство ещё не знает своей подсети (например, при запросе к DHCP).

Тип **статический**: устройств за этими записями нет, соответствие
задано системой, ARP не требуется.

### Multicast
224.0.0.2 все маршрутизаторы сегмента
224.0.0.22 IGMP — управление членством в группах
224.0.0.251 mDNS — обнаружение устройств в локальной сети
224.0.0.252 LLMNR — резолвинг имён Windows
239.255.255.250 SSDP/UPnP — автообнаружение устройств
Все MAC начинаются с `01-00-5e` — под IPv4-multicast зарезервирован
этот префикс, остальные биты вычисляются из IP-адреса группы.
Поэтому записи статические.

## 🔴 Замечание по безопасности: LLMNR и mDNS

Наличие записей `224.0.0.251` и `224.0.0.252` — поведение Windows
по умолчанию, но эти механизмы представляют риск.

**LLMNR** и **NetBIOS** — резервные механизмы разрешения имён. Если DNS
не нашёл имя, машина рассылает запрос в сеть и **верит любому, кто ответит**.
Та же наивность, что в ARP.

На этом построена популярная атака в корпоративных сетях: инструмент
**Responder** отвечает на все такие запросы «это я», получает попытку
аутентификации и **захватывает хеш пароля** для офлайн-подбора
или relay-атаки.

**Рекомендация:** отключение LLMNR и NetBIOS over TCP/IP — одна из самых
дешёвых и эффективных мер хардненинга Windows-инфраструктуры.

## Выводы

1. Проверка на ARP spoofing — одна команда и взгляд на колонку MAC
2. Для всего внешнего трафика используется только MAC шлюза
3. Не все записи в таблице соответствуют устройствам: broadcast
   и multicast задаются статически по формуле
4. Стандартная конфигурация Windows включает механизмы (LLMNR, mDNS),
   которые расширяют поверхность атаки без явной необходимости
