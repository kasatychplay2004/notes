# Лаба 1: Инкапсуляция и MTU

**Модуль 1, сессия 1** · Инструменты: Wireshark, ping (Windows)

## Цель

Увидеть инкапсуляцию на реальном трафике и практически определить MTU канала.

---

## Часть 1. Разбор структуры пакета

Захватил трафик на интерфейсе Ethernet, открыл сайт, разобрал TCP-пакет
(соединение к 213.33.201.6:443, HTTPS).

### Уровни в одном пакете

| Уровень OSI | Что видно в Wireshark |
|---|---|
| L2 канальный | `Ethernet II` — MAC источника и назначения |
| L3 сетевой | `Internet Protocol Version 4` — IP, TTL |
| L4 транспортный | `Transmission Control Protocol` — порты, seq, флаги |

### Адреса в кадре
Src MAC: d8:5e:d3:54:84:ef (GigaByteTech) — мой ПК
Dst MAC: e0:0e:e4:cd:e1:06 (DWnetTechnol) — роутер
Src IP: 192.168.1.72
Dst IP: 213.33.201.6
Порты: 59063 → 443 (HTTPS)

### Вывод: почему Dst MAC — это роутер, а не сервер

IP назначения `213.33.201.6` находится вне моей подсети `192.168.1.0/24`.
MAC-адресация работает только внутри одного сегмента сети, поэтому напрямую
адресовать удалённый сервер по MAC невозможно.

Кадр передаётся шлюзу, который дальше маршрутизирует пакет.
На каждом следующем участке MAC-адреса будут другими, а IP-адреса
останутся неизменными до самого получателя.

**Побочное наблюдение:** Wireshark расшифровывает первые 3 байта MAC (OUI)
в имя производителя. По вендору можно понять, что за устройство в сети —
рабочий приём при инвентаризации и расследованиях.

**Наблюдение по безопасности:** соединение зашифровано (HTTPS), содержимое
L7 недоступно. Но заголовки L2/L3/L4 видны полностью — шифрование
защищает данные, но не метаданные: кто, с кем и когда — видно всегда.

## Часть 2. Определение MTU канала

Отправлял ICMP-пакеты с запретом фрагментации (`-f`) и разным размером
полезной нагрузки (`-l`).

<img width="976" height="511" alt="preview" src="https://github.com/user-attachments/assets/d90647e2-da58-487e-8a67-0aee17b16c8a" />

ping -f -l 1472 8.8.8.8
Ответ от 8.8.8.8: число байт=1472 время=22мс TTL=105
Пакетов: отправлено = 4, получено = 4, потеряно = 0 (0% потерь)

ping -f -l 1473 8.8.8.8
Требуется фрагментация пакета, но установлен запрещающий флаг.
Пакетов: отправлено = 4, получено = 0, потеряно = 4 (100% потерь)

### Расчёт
1472 (данные) + 8 (ICMP-заголовок) + 20 (IP-заголовок) = 1500 байт

**MTU канала = 1500** — стандартный Ethernet без сужений.

### Что здесь произошло

Пакет в 1473 байта превысил MTU. Из-за флага DF роутер не мог его
фрагментировать и вернул ICMP-сообщение «Fragmentation Needed».
Это работающий механизм Path MTU Discovery.

**Практический вывод:** если бы файрвол блокировал этот ICMP, ошибки бы
не было — пакеты просто молча терялись бы. Это ситуация «PMTUD black hole»:
пинг проходит, соединение устанавливается, но передача больших объёмов
зависает без единой записи в логах.

Отсюда правило: блокировать ICMP целиком — вредная практика.
Фильтровать нужно избирательно, пропуская служебные типы
(Fragmentation Needed, Time Exceeded).

## Часть 3. Кодирование доменных имён в DNS

Разобрал DNS-ответ для `ext-strm-ruvoz01bln-01.strm.yandex.net`.

DNS не хранит имя как строку с точками. Используется формат
**length-prefixed labels** — каждая часть имени предваряется байтом
её длины, всё имя завершается нулевым байтом:
16 'ext-strm-ruvoz01bln-01' (0x16 = 22 символа)
04 'strm'
06 'yandex'
03 'net'
00 ← конец имени
<img width="893" height="251" alt="preview (1)" src="https://github.com/user-attachments/assets/46e4104b-5b1f-4dec-82c9-e509084ea239" />

**Ограничения формата:** одна метка — до 63 байт, полное имя — до 255.

**Почему это важно для ИБ:** ограничение длины напрямую влияет на
DNS-туннелирование — атакующий вынужден дробить данные на множество
запросов. Отсюда характерные признаки эксфильтрации: аномально высокое
количество запросов к одному домену и длинные высокоэнтропийные метки
вида `a7f3d9e2b1.tunnel.example.com`.

## Итоги

1. Инкапсуляция — не абстракция, а видимая структура каждого пакета
2. MAC меняется на каждом хопе, IP сохраняется до получателя
3. MTU проверяется практически, двумя командами
4. Блокировка ICMP «для безопасности» ломает работу сети
5. Шифрование не скрывает метаданные соединения

## Формулы

MSS (TCP) = MTU − 20 (IP) − 20 (TCP) → 1460 при MTU 1500
Данные (UDP/ICMP) = MTU − 20 (IP) − 8 → 1472 при MTU 1500
