# Лаба 2: TCP handshake и согласование MSS

**Модуль 1, сессия 2** · Инструменты: Wireshark, netstat

## Цель

Увидеть рукопожатие TCP на реальном трафике и проверить, как
согласуется MSS с измеренным ранее MTU.

---

## Захват

Фильтр отображения: `tcp.flags.syn==1`

Найденная пара пакетов одного соединения:
1986 192.168.1.72 → 5.252.34.95 54293 → 443 [SYN] MSS=1460
2006 5.252.34.95 → 192.168.1.72 443 → 54293 [SYN, ACK] MSS=1360
Порты сходятся крест-накрест — это одно соединение.

**Замечание по фильтру:** третий пакет рукопожатия (чистый ACK)
не отображается, так как фильтр отбирает только пакеты с флагом SYN.
Для просмотра полного обмена — Follow → TCP Stream.

---

## Наблюдение 1: MSS сошёлся с измеренным MTU

Мои исходящие SYN во всех соединениях предлагают **MSS=1460**.

Проверка формулой:
MSS = MTU − 20 (IP) − 20 (TCP) = 1500 − 40 = 1460 ✓
Совпадает с MTU=1500, измеренным в лабе 1 через ping с флагом DF.

---

## Наблюдение 2: серверы отвечают разными MSS

| Сервер | MSS в ответе | Предполагаемый MTU пути |
|---|---|---|
| 128.75.231.32 | 1460 | 1500 (прямой Ethernet) |
| 20.250.198.32 | 1440 | 1480 |
| 34.107.218.251 | 1412 | 1452 (туннель) |
| 23.216.134.158 | 1384 | 1424 |
| 5.252.34.95 | 1360 | 1400 (VPN/туннель) |

**Вывод:** каждый путь имеет своё узкое место. Значения 1400 и 1452 —
типичные для туннелированных соединений (VPN, PPPoE).

При согласовании выбирается **минимальное** из предложенных значений,
чтобы пакеты прошли через самый узкий участок пути.

Это практическое подтверждение механики Path MTU Discovery,
разобранной в лабе 1.

---

## Наблюдение 3: соединения по HTTP
57359 → 80 192.178.24.99 (диапазон Google)
57360 → 80 23.216.134.158
57361 → 80 128.75.231.32

Три незашифрованных соединения. Требуют внимания, хотя обычно это
проверки доступности сети или редиректы на HTTPS.

Привычка: при виде порта 80 задавать вопрос «почему без шифрования».

---

## Наблюдение 4: эфемерные порты

Исходящие порты (54293, 57359, 64817, 53766...) — случайные из верхнего
диапазона, свои для каждого соединения. Их разнообразие — норма.

**Анализировать нужно порты назначения.** Здесь только 80 и 443 —
обычная картина браузинга.

Признаком проблемы были бы исходящие соединения на нестандартные
порты (4444, 1337, 8888) к незнакомым адресам.

---

## netstat: привязка соединений к процессам
netstat -ano | findstr ESTABLISHED

Ключевое отличие от Wireshark: последняя колонка содержит **PID** —
идентификатор процесса, установившего соединение.
tasklist | findstr <PID>
**Практический смысл:** Wireshark показывает, что летит по проводу,
netstat — какая программа это делает. При расследовании инцидента
вопрос «кто установил это соединение» часто важнее содержимого трафика.

Соединение с подозрительным адресом от браузера — норма.
То же соединение от неизвестного процесса из временной папки — инцидент.

---

## Итоги

1. Рукопожатие TCP видно в трафике как последовательность
   SYN → SYN,ACK → ACK
2. MSS согласуется по минимальному значению из предложенных
3. Измеренный MTU (1500) подтверждён значением MSS (1460) в живом трафике
4. Разные MSS от разных серверов показывают разные узкие места путей
5. Анализировать следует порты назначения, а не эфемерные исходящие
6. netstat связывает соединение с процессом — то, чего не даёт Wireshark
