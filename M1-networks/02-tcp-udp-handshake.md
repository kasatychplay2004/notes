# TCP, UDP и three-way handshake

**Модуль 1, сессия 2**

## Зачем это нужно

Транспортный уровень — место, где безопасность становится осязаемой.
Сканирование портов, stateful-файрволы, SYN flood — всё построено на
механике этого уровня.

---

## Порты

IP приводит данные к машине, порт — к конкретному приложению.
Аналогия: IP = адрес дома, порт = номер квартиры.

Соединение однозначно определяется четвёркой:
`src IP : src port ↔ dst IP : dst port`

Поэтому можно открыть десять вкладок одного сайта — исходящий порт
у каждого соединения свой.

| Диапазон | Назначение |
|---|---|
| 0–1023 | системные службы |
| 1024–49151 | зарегистрированные приложения |
| 49152–65535 | эфемерные (временные порты клиента) |

## TCP vs UDP

**TCP** — заказное письмо с уведомлением: гарантия доставки, порядка,
подтверждения. Медленнее, накладные расходы.

**UDP** — открытка: кинул и забыл. Быстро, никаких гарантий.

UDP не «плохой TCP» — это осознанный выбор.

> Потеря данных хуже задержки → TCP
> Задержка хуже потери данных → UDP

| Критерий | TCP | UDP |
|---|---|---|
| Рукопожатие | да | нет |
| Гарантия доставки | да | нет |
| Гарантия порядка | да | нет |
| Заголовок | 20 байт | 8 байт |
| Скорость | ниже | выше |
| Подделать отправителя | трудно | легко |
| Применение | файлы, веб, SSH | видео, игры, DNS |

**Почему UDP легко подделать:** нет рукопожатия, никто не проверяет
отправителя. Отсюда атаки с усилением (amplification) — подставляешь
адрес жертвы, сервер шлёт ей огромный ответ.

**Почему TCP трудно:** чтобы соединение состоялось, надо ответить на
SYN-ACK. А он уйдёт по подставленному адресу, то есть не тебе.

## Флаги TCP

| Флаг | Значение |
|---|---|
| SYN | запрос соединения |
| ACK | подтверждение получения |
| FIN | корректное завершение |
| RST | аварийный сброс / отказ |
| PSH | передать приложению немедленно |
| URG | срочно (не используется) |

**FIN vs RST:** «до свидания» против «пошёл вон».
RST означает либо «на этом порту никого нет», либо «соединение сломалось».

Много RST в трафике = признак сканирования портов.

## Three-way handshake
Клиент Сервер
│ ─── SYN ──────────────────► │ "хочу соединиться"
│ ◄── SYN, ACK ────────────── │ "подтверждаю + сам прошу"
│ ─── ACK ──────────────────► │ "начинаем"
│ СОЕДИНЕНИЕ ГОТОВО │

**Зачем три шага:** обе стороны должны убедиться, что связь работает
в обе стороны. Как телефонное «слышишь меня? — да, а ты меня? — да».

Двух мало: сервер не уверен, что его ответ дошёл.

### ⚠️ Ключевой момент

**SYN-ACK — это ещё НЕ установленное соединение.** Это середина
рукопожатия. Соединение готово только после третьего пакета.

Именно этот промежуток — мишень SYN flood.

### Что согласуется

Помимо номеров — опции соединения, включая **MSS** (MTU − 40).
Берётся минимальное из предложенных обеими сторонами.

### Закрытие — четыре шага

FIN → ACK → FIN → ACK. Четыре, потому что соединение двунаправленное,
каждая сторона закрывает свою половину отдельно.

## 🔴 Атака: SYN flood

**Механика.** Между вторым и третьим шагом сервер обязан помнить
запрос — иначе не сможет проверить финальный ACK. Атакующий шлёт
тысячи SYN и никогда не отправляет третий пакет. Очередь ожидания
переполняется, легитимные пользователи не могут подключиться.

**Аналогия:** администратор в приёмной записывает всех желающих
на бланки. Звонят 10 000 человек, никто не подтверждает. Стол завален,
настоящего посетителя принять негде.

**Почему работает:**
1. Асимметрия — атакующему SYN стоит 40 байт, серверу память на десятки секунд
2. Сервер обязан хранить состояние по протоколу
3. Адрес отправителя ещё не проверен (проверка и есть смысл рукопожатия)

**Главное:** это не баг реализации, а следствие дизайна протокола.
Патчем не чинится, только обходные меры.

MITRE ATT&CK: T1498.001

---

## 🟢 Защита: SYN cookies

**Идея:** не хранить состояние вообще.

Вместо записи в очередь сервер зашифровывает всю информацию о запросе
в сам номер последовательности (ISN), отправляет SYN-ACK и немедленно
забывает. Память не выделяется.

Когда приходит ACK, клиент по правилам TCP возвращает этот номер —
сервер пересчитывает и восстанавливает состояние из самого числа.

**Аналогия:** гардеробщик перестал вести журнал и зашифровал всю
информацию прямо в номерок. Подделать нельзя — не зная секретной метки.

> Атака целилась в переполнение памяти. Памяти теперь не выделяется.
> Мишень исчезла.

**Цена:** теряется часть опций TCP. Поэтому включается автоматически
только при переполнении очереди. В Linux включено по умолчанию.

### Другие меры

| Мера | Суть |
|---|---|
| Anti-DDoS сервис | фильтрация до попадания в сеть |
| Rate limiting | ограничение запросов с адреса |
| BCP38 | провайдер режет пакеты с поддельными адресами |
| Балансировщик | держит рукопожатия за сервер |

> **От объёмной атаки нельзя защититься на самом сервере.**
> Если канал забит — ты уже проиграл. Защита строится выше по потоку.

## 🔵 Обнаружение

**На сервере:**
```bash
ss -tan state syn-recv | wc -l       # Linux
netstat -ano | findstr SYN_RECEIVED  # Windows
```
Единицы — норма. Тысячи — тревога.
Ядро само пишет в лог: «Possible SYN flooding. Sending cookies.»

**В трафике:**
- Резкий рост SYN при неизменном числе завершённых соединений
- Огромное разнообразие адресов источника
- Одинаковый TTL при разных адресах → подделка
- Одинаковый размер окна → пакеты сгенерированы одной программой

**Почему одинаковый TTL выдаёт подделку:** TTL уменьшается на каждом
роутере. Пакеты из разных стран физически не могут иметь одно значение —
они прошли разное число переходов. Одинаковый TTL = все пакеты пришли
из одного места.

### Атака или наплыв пользователей

| Признак | Пользователи | Атака |
|---|---|---|
| Соединения завершаются | да | нет |
| Активность после подключения | запросы | ничего |
| Разброс адресов | обычный | неправдоподобный |
| TTL | разный | одинаковый |

**Главный различитель — доходят ли соединения до конца.**

## Сканирование портов

Построено на манипуляциях флагами:
SYN → SYN-ACK = порт открыт
SYN → RST = порт закрыт
SYN → тишина = фильтруется
**Вывод для настройки файрвола:** молча отбрасывать (DROP) лучше, чем
отвечать отказом (REJECT) — атакующий не получает подтверждения,
что хост вообще существует.

---

## Что запомнить

1. SYN-ACK — середина рукопожатия, не финал
2. UDP легко подделать, TCP трудно
3. SYN flood атакует дизайн протокола, а не ошибку в коде
4. SYN cookies убирают саму мишень, а не защищают её
5. От объёмной атаки защищаются выше по потоку
